## The Agent Host: excluded, and why

`STATE.md` left open whether upstream's Agent Host stays. It does not.

| Question | Finding |
|---|---|
| Does it start in a default run? | Yes, before this item. `AgentHostPrewarmContribution` asks for it when the window restores. The packaged app built before B3 wrote `agenthost.log` into a fresh profile, with no chat sent |
| Is a Copilot session type reachable? | Yes, before this item: the chat input's session-target picker listed the Agent Host types, and "Open Agents Window" opened a second workbench (`sessions.html`) built around it. Only the *default* for a new chat had been moved back to the local harness |
| Does it send anything off the machine? | Not shown either way. Its telemetry is off without `enableTelemetry` and its model list makes no request without a token, but at startup it starts a closed-source runtime binary shipped in the SDK's platform package, and what that binary does cannot be read from this repository |
| Is there a setting that turns it off? | Only `chat.disableAIFeatures`, which also hides Onyx's own chat |

"No Copilot session type or tool is reachable and nothing leaves the machine" could not be shown, so the
other branch applies: exclude it. The exclusion uses upstream's own switch and one guard:

1. `IAgentHostEnablementService` is registered as "no Agent Host runtime available" (the web workbench's
   configuration). The pre-warm does not run, so the process is never asked for; the workbench contribution
   that registers the session types, the language-model vendors and the harness does not run.
2. `openAgentsWindow` in the main process returns without opening the sessions workbench, which has its own
   entry point and would otherwise bring its own Agent Host stack.

Evidence, checked by the packaged smoke and the end-to-end suite on every run: no `agenthost.log` in the
profile after several agent runs; "Open Agents Window" opens no second workbench. The unit test shows that
with the switch off no agent-host session type is usable even if a user turns upstream's harness defaults
back on.

**What is not done.** The Agent Host's bundle entry and the SDK's platform package (the runtime binary) are
still inside the application. Nothing in an Onyx run starts them. Taking them out means changing the build's
dependency packaging and its version assertions, which is larger than this item and belongs with D8's
dependency review. Until then "Onyx ships no Copilot" is true of the extension and of anything that runs, and
not of every file in the bundle; `docs/SUPPORT.md` says so.

## Decisions made inside the item

- **One opt-in, and it is network.** DEC-03 allows browser and MCP opt-ins that keep every gate. The network
  opt-in admits three reviewed tools; each network call asks in an Onyx dialog that shows the tool and its
  arguments, because core's own confirmation can be switched off by core settings. MCP has no opt-in: an MCP
  tool cannot be classified from a table, and one that writes would bypass Onyx Changes.
- **`remember` asks, and says where the text came from.** The origin is the user's request, the output of a
  named tool in this run (the whole note, or any five consecutive words of it), or the model. Text that
  arrived in a tool result gets the warning style. Pins and playbooks have no model-facing writer, so the
  memory tool is the only row with the `persist` capability; the table's test pins that.
- **Reads that leave the workspace files are excluded.** Core's terminal and task output readers are
  read-only, but what they read is not the workspace and may hold secrets.

## Found and not changed here

- The command "Open Agents Window" still appears in the palette and now does nothing. Hiding it needs a
  context key that upstream also uses to gate opening chat at all.
- `scripts/code.sh` with `ONYX_DEV_COPILOT=1` loads the Copilot extension; its tools are not in the contract,
  so they are refused like any unknown tool. Not tested here.
- **A harness defect that hid failures.** `@playwright/cli run-code` prints the script it ran after the value
  the script returned, so a check such as `output.includes('approved:')` is true whether or not the script
  returned it. The dialog checks added in B2 and B3 and three older ones (the inline-edit widget, the Stop
  button, the rename pick) now compare the returned value (`pwValue`). One of the three had been passing on
  the echo alone: "a streaming run can be stopped from the control plane" found no Stop button, because
  sending a chat message hides the Control Plane. The run was never stopped; it simply finished. The suite
  now reopens the Control Plane first and the click happens. Stop's own semantics are B10's (Module 3).
- The bundle still holds the SDK's platform package: 169 MB under
  `node_modules.asar.unpacked/@github/copilot-sdk-darwin-arm64` in the app built here.
