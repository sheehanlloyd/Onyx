## Decisions made inside the item

- **First terminal status wins.** `complete()` after Stop changes nothing, and so does a second Stop. The
  journal holds one outcome a run.
- **Ending a run any way but completing cancels its token.** A failed or out-of-budget run should not leave
  a request or a command behind either. Code that asks "was this cancelled?" has to ask before it ends the
  run; the loop had two places that asked afterwards, and both would have swallowed an error message.
- **A pause lasts ten minutes at most**, then the run ends as `budget-exhausted`. The plan says a run has a
  time budget and does not give a number; the rig's watchdog is fifteen minutes.
- **The turn cap is `budget-exhausted`**, not `completed` with an incomplete result.
- **A tool call that was already handed to the tools service when Stop came** is refused there before the
  tool is entered, as the product's tools service does; the tools check again themselves.

## Found while doing this

- **The rig's stop step did two things**: it pressed the control plane's Stop and cancelled the chat request.
  The audit's finding is about the first alone. With both, a control plane that cancelled nothing still
  passed once the loop listened to the request's token. The step is now the Stop button alone, which is the
  path R-15 names; the mutant is detected only that way.
- **The Module 2 gate's table check required a non-empty table** ("not empty by accident"). It now accepts
  an empty one when Module 3's gate file runs the 20,000-episode campaign, which is what makes emptiness
  deliberate. Its other two assertions are unchanged.

## Not done here

- **An open approval dialog is not closed by Stop.** Its answer is ignored. Closing it needs a dialog that
  takes a cancellation, which the platform's prompt does not.
- **One-shot flows** check their own token when they decide what to say afterwards, so a review stopped from
  the run list can show its "failed" notice although the run is recorded as stopped.
