## Where this departs from the plan's wording

The plan says to cap the hold at 400 characters. Applied to every hold, that would release any tool call
longer than 400 characters as visible JSON instead of running it, and the supported model writes its tool
calls as text: an `editFile` call with a real replacement is longer than that as a matter of course. The
defect the plan describes is text being held on a guess. So the 400-character cap applies to what is
undecided, and a reply that has shown itself to be a call (its first key, and the tool it names) is held to
its end. The long-call case is in the regression. Before this item the limit was 4,000 characters for
everything, which already cut long calls loose; it is 32,000 for a recognised call now.

## Decisions made inside the item

- **The tool's name decides early.** `{"name":"my-package"` is released at `my-`, because no tool on offer
  starts that way. Without the names the decision could only be made at the end.
- **An unmarked fence is treated like a `json` fence** until its first character says otherwise, because
  models wrap calls in bare fences.
- **`{"type":"function", …}`** is held as a call; `{"type":"module", …}` is not.

## Found while doing this: a file-sync service is writing into the working tree

While this item's checks were running, the hygiene check failed on files nobody had written: 22 untracked
copies named `<name> 2<.ext>` had appeared in the clone, among them eleven upstream workflows that Module 1
deleted (`pr 2.yml`, `pr-darwin-test 2.yml`, …), `CODEOWNERS 2`, `CODENOTIFY 2`, a second image manifest,
and second copies of the A1 to A7 reports. Their dates were from the Module 1 session.

- Cause: the repositories live under the user's Desktop folder, and the Desktop folder is synchronized by a
  cloud drive (the Finder setting is on and the drive's status shows it active). Those names are the names
  it gives conflict copies.
- Every one of the 22 was byte-identical to a blob already in this repository's history, none was tracked,
  and none had ever been committed. They were removed.
- The owner's checkout showed no such files, and its `git status` was unchanged.
- A directory-wide `git add` would have committed them. A `sync-duplicates` hygiene check now fails on any
  file with such a name under the Onyx paths, `.github` and `docs`, with a test.
- This can happen again at any moment, to either checkout, and a sync service rewriting files under a
  running build is a hazard beyond stray copies. Moving the repositories out of the synchronized folder, or
  excluding them from the drive, is the owner's to do.
