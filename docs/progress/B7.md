## Found while doing this: the rig's users never acted after a run

The simulation rig has six boundaries at which a scripted or generated user may act. One of them,
`afterRun`, was never raised: the rig only observed the state there. Every user step scheduled after a run
was silently skipped. That includes the accept-all of the edit scenario and both audit scenarios that
Module 1 and Module 2 reported as holding I-09 (Codex N2, Claude H4), and one in six of the generated
steps. Those scenarios passed because nothing happened in them.

The rig now raises the boundary before the run and after it, as many times as steps are scheduled. A new
test runs the four scenarios with user steps and asserts how many steps were carried out and what the
buffer holds afterwards. With the steps running, the 2,000-episode campaign found one thing, in the rig:
it recorded a review that had moved (after an accept or a rebase) as a new staging, and judged the earlier
SEARCH text against the new base. A stage event is now a new generation and nothing else.

The statement in `HARNESS-CONTRACT.md` that I-09 "holds in the rig" for N2 and H4 is corrected there.

## Decisions made inside the item

- **A new generation replaces every id.** The plan allows an id to survive when the agent's replacement for
  that hunk is unchanged. Here any new staging of the file renames all of its hunks, so a review made before
  it can never be accepted. It is the stricter reading, and simpler to state to the user.
- **A hunk is its own lines plus up to three unchanged lines each side.** At the top or bottom of a file there
  are fewer lines to take and the rule is the same. Found once: carried there, same id. Found nowhere or
  twice: a conflict, with both texts, never applied. A hunk that would land before one already placed is a
  conflict too.
- **After an accept, the rest move by arithmetic**, not by searching: the buffer is the old one with the
  accepted hunks applied. If the buffer is anything else, the rest are found by context.
- **Accept the whole file with a conflict on show is refused.** It means "apply what I was shown", and part
  of that cannot be applied.
- **The outcome of an accept is a value with a reason**, and the user also gets the notification.
- **Size limits are Section 15's**: 1,000 lines a side, 1,000,000 table cells, 256 KiB together. C9 raises
  the first two.

## Not done here

- **The Changes view is not instantiated in the rig**; the view's accept and reject buttons are exercised by
  the end-to-end suite. C1 adds the diff editor and R-25.
- **Inline edits do not go through the change set yet** (B9), so the size guard does not cover them yet.
- **A restored oversized proposal** is refused with a notification; that path is exercised by the pure
  function it calls, not by a test that restarts the service.
