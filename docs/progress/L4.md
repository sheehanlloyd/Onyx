## How "behaviour identical to before L4" is shown

The plan's test is the default configuration against the trace corpus. The committed trace corpus is L8's,
in Module 3. Until it exists the corpus is the simulation rig's: before the loop was touched, the digest of
the rig's trace for seeds 1 to 1,000 and for every scripted scenario was written to
`onyxSimBehaviourBaseline.ts`, at 7055ed1faa3. A rig trace is every request, chunk, tool dispatch, dialog,
staged edit, buffer change, status and timeline entry of a run under virtual time, so the same digest is the
same run. After L4 all 1,000 and all the scenarios have the digests they had.

Two consequences:

- The file is a snapshot of behaviour. An item that changes the loop's behaviour on purpose regenerates it
  with the command in its header and says why. Module 3's first such item will; L8 then replaces it with the
  trace corpus and its first-divergence report.
- It shows the rig's runs are unchanged. It does not cover what the rig does not instantiate (the views, the
  inline-edit controller). The end-to-end suite and the packaged smoke cover the product end to end.

## Decisions made inside the item

- **The configuration is flat.** A field is a switch; a manifest names switches; a diagnostics export
  carries switches and drops anything nested.
- **A lab value is any value the product would not have derived**, and a packaged build refuses a request
  whole, even one that asks for exactly the default. Deciding field by field which values are "shipping"
  would leave a path for a manifest to steer a packaged build.
- **The request comes from the environment** (`ONYX_LAB_MANIFEST`), read in the shared process. No setting,
  no command-line flag (which would mean touching upstream's argument parser), nothing in the workspace. A
  manifest that cannot be read is still a request and is refused in sight.
- **One wrong field refuses the whole request.** A half-applied configuration is a third configuration
  nobody asked for.
- **Where a manifest is on disk is never recorded.** The trace names the manifest and the entry.
- **Sampling is not harness configuration.** Temperature, seed and the output cap stay in the trace's
  sampling record, as the manifest has them.
- **A run with no tools is not constrained**, whatever the protocol says: there is no call to constrain.
  That was so before and is now said where the protocol is read.

## What the plan asked for that is partial

- **"Edit protocol", "eviction policy" and "tool-slot policy" have one value each.** The alternatives are
  L7's and L17's to add. Asking for any other value is refused with that reason.
- **The profile produces the configuration; the datasheet does not yet.** L5 is next and feeds the profile.
- **"Once L8 exists, trace conformance shows that introducing the configuration changed no behaviour."** L8
  is Module 3's. The rig baseline above stands in for it.
- **`readToolLineNumbering: false` leaves the tool's description saying its lines are numbered.** Recorded
  as a limit in docs/SUPPORT.md.

## The packaged layer

Two checks in the packaged smoke, release mode:

- The app is started with a manifest that asks for a one-turn run. Every run's trace header must say
  `source: default`, name the entry that was asked for, give the refusal, and not have a turn cap of 1. If
  the request were applied, the smoke's multi-turn flows could not complete either.
- The built app is scanned for every mutant's id and for the rig's markers. On the app built from this tree:
  see "Integration run".

`r44-bundle-scan.test.mts` keeps the scan honest without an app: it finds all 28 markers in the development
output, where tests are compiled too, and none in the compiled product folders.
