## What a campaign is

A manifest names models, seeds, harness configurations and a task set. The launcher plans every combination, ordered by model. Tier S asks each model once a task from plain Node. Tier A starts the application on a linked worktree in the temporary directory and hands it a work order through `ONYX_LAB_CAMPAIGN`; the engine inside sends each unit as a chat request, so the run has the tools, the staging and the journal a user's request has. It writes one record a unit: the journal without its prompt snapshots, every edit the run asked to stage as it was sent, and the file as the run proposed it. The launcher scores records afterwards, and `--rescore` does it again from what is committed.

## The real-model campaigns

A private Ollama 0.33.0 on port 11500, started with `OLLAMA_CONTEXT_LENGTH=16384`. That gives every model the 16,384-token context B15 verified, by the server's own setting: no alias is created on the runtime and nothing is asked of it. The datasheets were measured again on that server (`2026-11-22-datasheets/`): for each of the three installed models "16384 tokens verified (requested nothing, reported 16384); a prompt past it lost its start".

**These campaigns show that the engine runs. They rank nothing.** Eight and four tasks are far below any sample this module's studies need, and the machine was busy: the load average rose past 30 while they ran (the file indexer and the cloud-file daemon, after a build). The 7B model generated at about 23 tokens a second in the datasheet run and 10 to 19 in the campaigns, against 49 measured on an idle machine on 2026-11-21. No throughput number from these runs should be quoted.

What they do show about the models, and it is carried into L10's task design as pilot evidence, not as a result (this describes the first tier A run, at temperature 0.2; see the Erratum): asked "In the file X, make this change: <commit subject>", `qwen2.5-coder:7b` answered three of four tier A tasks in prose without calling a tool (one reply asks the user for the CSS to change) and read the file in the fourth before saying the change could not be made; `qwen2.5-coder:1.5b` read the file in all four and then said the change had been made, without proposing an edit. In tier S the two Qwen models' edit blocks could not be placed in 8 of 16 replies.

## Erratum, 2026-11-22: the first tier A run did not send the sampling it recorded

Found while reading the first records of L13's campaign, before any hypothesis result existed. The loop wrote a campaign's seed and temperature into the trace header, and the model provider sent the model profile's own: temperature 0.2 and no seed. R-49's check, "the seed was on the wire", read the trace, so it passed. It now reads what the mock runtime received (`/debug/recent-chats`) and was seen to fail with `undefined/0.2` before the fix (`b6ddfa66aa9`): the loop now sends a campaign's seed and temperature with each request and the provider honours them over the profile.

What it invalidated, and what was done:

- `2026-11-22-engine-tier-a` as first committed (8 units, 106 s) claimed temperature 0 and seed 1 and ran at 0.2 with no seed. It is replaced by a second run of the same manifest, with the fix and with L10's instruction; the table above shows the second run. The paragraph below about how the models answered describes the first run, which is no longer in the repository; it is kept because L10's instruction was decided from it.
- The two pilots of L10 ran the same way. They are design evidence and were never committed; Amendment 1 says so.
- L13's campaign had recorded 17 units. It was stopped, its records were deleted, and it was started again from nothing.
- The tier S campaign sends its seed and temperature itself, from the launcher, and was not affected.

The pinned Ollama does not echo a seed, so a trace of a real run says `honoured: unknown`; that the seed is sent is checked against the mock, which echoes it.

## The estimate

`estimateLabDuration` multiplies the plan by a unit's assumed shape (turns, tokens out and in) and each model's measured generation speed from the datasheet. The tier A estimate was six times too high here (10 minutes against 106 s): it assumes four turns of 220 tokens, and these runs took one or two short turns. The shape is a constant in `onyxLab.ts`; the studies record estimate and actual for every campaign, and L13's estimate is made from this campaign's measured seconds a unit, not from the constant.

## Scope notes

- **The index-fresh signal.** After a checkout the engine awaits `ensureWorkspaceIndex`, which reconciles the index against the tree before it resolves. It does not wait for the file watcher's own events.
- **The context.** `OLLAMA_CONTEXT_LENGTH` on a server started for the campaign replaces B15's alias here. The product's own path (an alias, after consent, verified by a canary) is not exercised by a campaign.
- **Extensions are off** in a campaign's instance (`--disable-extensions`): no language server runs, so the verification feedback of a run compares an empty set of problems with an empty set.
- **A stale launcher.** A launcher killed with SIGKILL leaves its worktree; the application stops when the heartbeat is 30 seconds old, and the next tier A start removes the folder and the worktree. Not tested: the check kills a tier S launcher, which has neither.
- **`could-not-serve` in tier S** also covers a task whose file is over `maxBeforeChars`: a model is not scored on a task it could not read. L10 keeps such tasks out of a task set instead.
- The engine is product code that a packaged build never runs. It is in the bundle, as the harness configuration service's refusal is.
