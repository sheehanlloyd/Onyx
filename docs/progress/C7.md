## The retrieval figure that was published is not what the tree measures

The plan asks that published retrieval measurements run through the production index. They now do, and the
number is lower than the one in the README.

- Published: 9 of 10 questions find the right file in the top 5 (the chart, and ONYX.md).
- Measured now, production index, 18,205 files of this repository at 100% coverage: **7 of 10**.
- The cause is not the wider corpus. The August method (every `.ts` under `src/vs`) run on today's tree
  also scores 7 of 10 and misses the same three files. The tree changed under a figure nobody re-ran: the
  move to upstream 1.147 brought files that outrank two of the answers, and the repository's own prose
  outranks the third.
- The misses: `onyxChangeSetService.ts` ranks tenth, behind README.md, ONYX.md and a review file;
  `onyxTerminalPolicy.ts` is outside the top 25, behind upstream's tool-approval tests and the B2 and B5
  progress reports; `onyxRouterService.ts` is outside the top 25, behind upstream's local-model bridge.
- What was changed: the benchmark; docs/BENCHMARKS.md, which now states the corpus, the result and the
  misses; ONYX.md's line; a sentence under the chart in the README giving 70%; the image manifest's rows
  for the two charts that carry the old corpus's numbers.
- What was not changed: the chart itself. `make-charts.mts` draws only from a manifest (L3), and a
  retrieval campaign with a manifest is C8's. Until then the README shows the August chart with the current
  figure in words directly under it.
- What was not done: ranking was not tuned to recover the three. That would be fitting the product to ten
  questions its author wrote. That documentation and tests outrank the implementing file is a real property
  of the ranking and is recorded here for C8.

## The cap

20,000 files and 256 MB of text, from the measurements in docs/SUPPORT.md. It covers this repository in
full at 284 MB of retained memory in the shared process, where the earlier cap held 27% of it at 74 MB.
Memory follows the text indexed (1.3 to 1.6 times its size), so the text cap bounds it near 400 MB. A
smaller workspace costs what it holds. If 284 MB for a workspace this size is more than the owner wants as
a default, the number to change is `ONYX_INDEX_LIMITS.maxFiles`: at 12,000 this repository's source and
neutral files are all held (11,964 of them) at 185 MB, and only tests and documentation wait.

## Decisions made inside the item

- **Order within source: nearest the root first.** With plain path order a cap of 5,000 kept the built-in
  extensions' `src` folders and cut `src/vs` short, because `extensions/` sorts first.
- **Writing the index could not stay as it was.** Raising the cap fourfold made an existing stall a long
  one: the index was serialised in one piece on the process that relays model output. It is written in
  batches of 64 documents now, and less often: 5 seconds after a build, at most once a minute while files
  change. A file older than the tree is brought up to date on load (B12), so the delay costs a few re-reads
  after a crash and nothing else.
- **A new file at the cap waits.** Before, a change to any eligible file added it to the index even when the
  index was full, so a capped index grew past its cap. Now it is counted as eligible and waits for the next
  load.
- **The persisted format is 3.** A file written by an earlier build is rebuilt, as any file that is not this
  index is.
- **The file cap is a user setting.** A workspace cannot raise the memory Onyx uses for it. The exclude
  settings are the workspace's, as they are for the explorer and the search.

## Limits, stated

- **`.gitignore`:** the root file only; negations are not applied (the file stays out); a folder-only
  pattern also leaves out a file of that name. Each errs towards leaving a file out.
- **Exclude settings:** a pattern conditional on a sibling file is not applied (the file is indexed); a
  negated pattern is not applied (the file stays out).
- **`eligibleFiles` on a truncated index** counts files past the cap by path alone, so it can be high by the
  few files over 256 KB. On this repository at a cap of 5,000 it reads 18,283 against a true 18,212.
- **The text cap** is applied at build and reconcile, not on each later change.
- **The walk** lists at most 400,000 directory entries; past that the index says it is truncated.

  working tree, so it is run after the commit.
