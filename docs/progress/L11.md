## The reference machine's scorecard

`docs/research/results/2026-11-22-reference-measure/scorecard.md`. The command chose 18 tasks by the product's rule from the repository at `126d11c7c9e`, all held out for the three installed models, and gave each model one request a task at temperature 0, seed 1.

| Model | Scored tasks | Reproduced exactly | Mean score | Lines removed that the author kept |
|---|---|---|---|---|
| qwen2.5-coder:7b | 18 | 0 | 0.08 | 28 |
| llama3.2:3b | 18 | 0 | 0.01 | 168 |
| qwen2.5-coder:1.5b | 18 | 0 | 0.01 | 175 |

It ranks the 7B first. That ranking is of closeness to the author's change: no model made the author's change on any task. It took 1,095 seconds against the 422 the command itself estimated from the datasheets, and the launcher's own estimate, made for a different shape of work, was 7,930.

**The first run did not finish.** It was stopped by hand after 20 minutes, with `llama3.2:3b` at 34,174 generated tokens in answer to one task. No one-shot request in the product sent an output cap. `NOTES.md` in the results directory has the evidence and the fix; the scorecard above is from the build with the fix.

## The catalog

The plan asks for the catalog to be re-measured and its 2024 defaults replaced where the measurement says so. Three of its six models are installed on the reference machine, and nothing is downloaded in this module, so three were measured.

- **qwen2.5-coder:7b** said "reliable tool calls". Measured: 0 of 5 requests used the runtime's tool-call channel, and 5 of 5 were readable as text. The note now says that.
- **llama3.2:3b** now says what was measured: it uses the channel as designed (5 of 5), and it is the weakest at editing existing code (168 lines removed that the author kept, over 18 tasks).
- **qwen2.5-coder:1.5b** keeps its note. Its claim is about latency, and the datasheet does not contradict it (first token 36 to 40 ms warm).
- **The 14B, 32B and GPT-OSS notes are not measurements.** They say things like "noticeably better at multi-file edits". The catalog's header now says they are unmeasured; their wording is unchanged and is for Module 5's pass over what the product says about itself.
- **The seed profile's numbers** (`common/onyxSeedProfiles.ts`: tool-call quality by size class) are unchanged. A measured datasheet already overrides them for a model that has one, which is the mechanism L5 built.

## Red before green

- `OnyxOneShot` failed against the code as it was: the request's options had no `maxTokens`. It passes with the fix.
- The six end-to-end checks found one defect when first run: two models with the same name on two endpoints were merged into one row. Models are now named by their key when ids collide.
- `OnyxScorecard` had one wrong expectation of its own (an order of strings), corrected.

## Scope notes

- **A reply cut at the output cap** is scored as it stands, and the scorecard does not say which replies were cut. Not fixed here.
- **"Should I Switch Models?"** was not run on the reference machine: it needs accepted requests in a workspace with `onyx.lab.requestTasks` on, and a campaign's instance has none. It is covered by the pure suite.
- **The supported matrix.** The command ran end to end on the one machine there is. LM Studio was not started; LM Studio results are not measured.
- **The README.** The measured claims of its benchmark section already linked their raw report. This item adds a pointer to the reference scorecard and changes nothing else on that page.
- **Community scorecards.** The directory exists with its rules. It is empty.
