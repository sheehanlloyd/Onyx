## Method (R-29)

Each case runs in its own Node process, which imports the compiled `common/onyxInlineEdit.js` from `out/`,
builds two texts of 6,000 lines, and diffs them five times, once, or not at all. The time is the best of
five. The memory is the peak resident size of the process that diffed once minus that of the process that
did not, so typed arrays count. Targets: 40 ms and 16 MiB with 60 scattered edits; 150 ms and 48 MiB with
nothing in common. The time targets are for the reference machine class and can be switched off elsewhere
(`ONYX_R29_SKIP_TIME=1`); the memory targets and the correctness hold anywhere. CI runs the check with the
time targets off for that reason: see "Not done here".

## Decisions made inside the item

- **Bounded, with a coarser answer past the bound.** Myers' search costs time and memory in proportion to
  the lines that differ. At 2,000 differing lines the worst case keeps about 16 MiB of search history;
  beyond it the function returns one hunk over the changed region. A proposal that rewrites more than 2,000
  lines is reviewed as one piece. The alternative, a linear-space variant with no bound, takes a third of a
  second on two unrelated 6,000-line texts, in the renderer.
- **The same hunks as before, where there was no choice.** No scripted scenario's trace changed. Where two
  shortest scripts exist the new search may pick another than the table did; the property test holds it to
  "shortest", not to "the same as before".
- **A size guard stays.** Nothing quadratic is left to protect, but a proposal is also stored across a reload
  and rendered. 20,000 lines and 1 MiB are bounds for that, chosen by judgement.

## Not done here

- **The time targets are not enforced in CI.** A shared runner is not the reference machine. See the
  workflow note; the memory and correctness halves run there.
- **The Changes view still renders every line of an expanded hunk.** A one-hunk proposal of thousands of
  lines is slow to expand. Not measured here.
