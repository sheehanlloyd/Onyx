## H-9: supported, on the scripted runs, with a condition that was met by nothing happening

*A cache-aware eviction policy re-processes fewer prompt tokens per turn than oldest-first at equal task success.*

**The scripted runs.** A fixed transcript of 16 turns, each tool result 4,000 characters, planned by the product's own `planTurn` for a context of 8,192 tokens; both pinned models, three repetitions, three policies: 18 runs, 288 turns, 1,731 seconds.

| Policy | Re-processed tokens, turns 2 to 16 | Ratio to oldest-first | Mean time to first token |
|---|---|---|---|
| oldest-results-first (the product) | 365,920 | | 8,062 ms |
| block-to-low-watermark | 153,178 | 0.42 [0.38, 0.47] | 3,343 ms |
| placeholder-results | 339,187 | 0.93 [0.90, 0.95] | 8,460 ms |

Block eviction's ratio is under the registered 0.70 and its interval excludes 1.

**How the tokens were counted is the deviation Amendment 3 recorded in advance.** The probe (`probe.jsonl`) sent one prompt twice: the runtime reported 2,963 prompt tokens evaluated both times, in 6,296 ms the first time and 22 ms the second. So `prompt_eval_count` is the size of the prompt, not what was evaluated, and the registered quantity is not reported by this runtime. Re-processed tokens are estimated as a turn's prompt-evaluation time over the time a token took in the same run's first turn. That estimate inherits whatever else was using the machine while a turn ran; the runs were made with nothing else of this project running.

**Placeholder replacement saves almost nothing**, in the simulation (R-56) and on real models alike. Replacing the oldest result's text changes the prompt as near its start as dropping the result does, so everything after it is processed again either way.

**The agentic runs** were to supply the other half of the hypothesis, equal task success: the three policies on 20 tasks with both models at a context of 8,192 tokens, 120 runs in 536 seconds.

| Policy | Succeeded | Runs in which anything was evicted |
|---|---|---|
| oldest-results-first | 0 of 40 | 0 |
| block-to-low-watermark | 0 of 40 | 0 |
| placeholder-results | 0 of 40 | 0 |

No run evicted anything, under any policy, even at half the product's context: these models' runs are two or three turns long (L13, L15). And no run succeeded. The registered condition, "its success rate is not lower by more than 2 points", is met, because the difference is zero in every resample. It is met by nothing having happened. This campaign says nothing about whether block eviction costs task success; it says that on these models and tasks no policy is ever exercised.

By the thresholds as registered the outcome is **supported**. What is supported is the first half: when eviction does happen, evicting in blocks re-processes less than half as much.

## What is adopted

`block-to-low-watermark` is a value of the harness configuration's eviction switch (L4), as the plan asks of a supported policy. **The product's default is unchanged: oldest-results-first.** The default was not changed because the only evidence about task success under the new policy is the empty table above, and a default that drops more context than it must is a change to be made on evidence that it does not hurt. `docs/SUPPORT.md` records this. `placeholder-results` stays in the code as the third arm of the study; nothing recommends it.

## Scope notes

- **The low watermark is 0.6 of the message budget**, fixed in Amendment 3 before the runs. No other value was tried.
- **The scripted transcript is one transcript.** Every tool result is the same size, and the budget is reached at the same turn in every run. The interval is over turns, not over transcripts.
- **The estimate caps a turn's re-processed tokens at the prompt's own size**, so a turn slowed by something else cannot count for more than everything.
