## The real-model traces

Recorded against a private Ollama 0.33.0 on a loopback port, stopped afterwards; nothing was pulled, created
or removed. Two workflows for each pinned model, at temperature 0 with seed 1.

| Trace | Model turns | What happened |
|---|---|---|
| `model-qwen2.5-coder-7b-read-then-edit` | 4 | Read the file (a call written as text, repaired), then two `editFile` calls that were both refused, then gave up in prose. Nothing was staged |
| `model-qwen2.5-coder-7b-answer-from-a-read` | 2 | Read the file, answered in one sentence |
| `model-qwen2.5-coder-1.5b-read-then-edit` | 3 | A read inside a code fence, an `editFile` call that was refused, an empty reply. Nothing was staged |
| `model-qwen2.5-coder-1.5b-answer-from-a-read` | 1 | Described the tool call in prose instead of making it |

These are what the models did, not what one would wish to show. Neither model staged an edit in its
recording: the 7B model's two attempts and the 1.5B's one were refused by the exact-or-refuse rule or by the
argument check. That is a result worth having in a corpus whose job is to notice when the harness starts
treating such replies differently. It is two prompts a model and says nothing general.

## Decisions made inside the item

- **A trace is a run that can be run again.** It holds the world (the rig's fixture files, the request, the
  user's steps) and the model's responses, and the expected events. It is not a journal to be parsed back
  into a run: the rig runs it.
- **Tool results are recomputed, not served back.** The plan has the replay feed recorded tool results back
  through the harness. The rig's tools are the product's own and its disk is in the trace, so they are run
  again and their results are among the events compared. This is stricter: a tool whose output changed is
  reported, where a served-back result would have hidden it.
- **Recording a real model takes turns with it.** The rig runs under virtual time; left to run in real time
  it stalled after the model's first reply. So the episode is run with the turns recorded so far, the first
  request past them is caught, the model answers it outside the rig, and the episode is run again. The rig
  is deterministic, so a turn's request is the same each time round. A recording is kept only if it then
  replays.
- **A reason is one line and has to be new.** An expected trace cannot be replaced silently, nor by
  repeating the reason it had.
- **The journal of the recording is kept for the report only.** What is compared is the rig's canonical
  event sequence, which has no run ids or wall-clock times in it.
- **The file is `onyxSimReplay.ts`,** not `replay.ts` as the plan has it, to follow the folder's names.

## Limits

- **The corpus is as wide as the rig.** Workflows that need an editor area or a real terminal are not in it.
- **A change to a scripted scenario or to a persona's generator needs a re-recording**, and the first test
  says which traces moved.
- **Cut-point mode against a real model** is the same live source the recorder uses; it was exercised with a
  scripted continuation and with a live function, not with a model.
- **The first recording run of a real model was stopped by hand** after ten minutes (the stall above).
